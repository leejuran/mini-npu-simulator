# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 N×N 패턴이 **십자가(Cross)** 인지 **X** 인지 판별하는 Python 콘솔 프로그램입니다.
NPU가 하드웨어로 병렬 처리하는 곱셈·누적 연산을 반복문으로 직접 구현하고, 크기에 따른 연산 시간 변화를 측정합니다.

- 외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `math`, `re`, `os`, `sys`, `unicodedata`)만 사용
- Python 3.8 이상 문법으로 작성 (Python 3.14.7에서 실행·테스트)

## 구현 요약

### 데이터 구조
`Matrix` 클래스가 N×N 값을 2차원 리스트로 저장하고 `get(row, col)` / `set(row, col, value)`로 특정 위치를 읽고 씁니다.
`from_rows()`는 만들 때 정사각형 여부, 행 길이, 숫자 여부를 검증합니다. `True/False`(Python에서 1/0으로 계산됨)와 `NaN`/`inf`는 거부합니다.

### MAC 연산
```python
total = 0.0
for i in range(n):
    for j in range(n):
        total += a[i][j] * b[i][j]   # 같은 위치끼리 곱하고(Multiply) 누적(Accumulate)
return total
```
벡터화 라이브러리 없이 이중 반복문으로 N×N번 곱하고 더합니다. 패턴과 필터 크기가 다르면 계산하지 않고 `ValueError`를 냅니다.

### 라벨 정규화
data.json은 같은 뜻을 다른 표기로 씁니다. 비교 전에 모두 표준 라벨 두 가지로 바꿉니다.

| 원본 | 위치 | 표준 라벨 |
|---|---|---|
| `+`, `cross` | expected 값, 필터 키 | `Cross` |
| `x` | expected 값, 필터 키 | `X` |

대소문자와 앞뒤 공백은 무시합니다(`"X"`, `" Cross "`도 인식). 해석할 수 없는 값(`"o"` 등)은 `None`이 되어 `[라벨]` FAIL로 처리됩니다.
정규화하지 않으면 `"+" != "Cross"`가 되어 정답인데도 FAIL이 나므로, **출력과 PASS/FAIL 비교는 모두 표준 라벨 기준**입니다.

### 동점 처리 정책 (epsilon)
```python
EPSILON = 1e-9
if abs(score_a - score_b) < EPSILON:  → UNDECIDED (모드 1에서는 "판정 불가")
else: 점수가 높은 쪽
```
- 부동소수점에서는 `0.1 + 0.2 = 0.30000000000000004`처럼 수학적으로 같은 값도 미세하게 달라집니다.
- `>`로만 비교하면 이 오차가 판정을 결정해 버리므로, 차이가 `1e-9`보다 작으면 판정하지 않습니다.
- UNDECIDED는 Cross도 X도 아니므로 expected와 같을 수 없고, 항상 **FAIL**입니다.
- 점수는 `repr()`로 출력해 `0.8999999999999999` 같은 오차를 숨기지 않습니다.

### 검증과 FAIL 사유 범주
모드 2는 문제가 생겨도 예외로 멈추지 않고 **케이스 단위로 FAIL** 처리합니다. 사유에는 원인 범주를 붙입니다.

| 표기 | 원인 분류 | 예시 |
|---|---|---|
| `[스키마]` | 데이터/스키마 | 키 형식(`size_N_idx` 아님), 필드 누락, 필터 없음·로드 실패, input 형식 |
| `[크기]` | 데이터/스키마 | 키는 5×5인데 input은 4×4 |
| `[라벨]` | 데이터/스키마 | expected `'o'` 해석 불가 |
| `[동점]` | 수치 비교 | \|Cross−X\| < 1e-9 |
| `[판정]` | 로직(또는 데이터) | 판정 Cross ≠ expected X |
| `[예외]` | 예상하지 못한 오류 | 위에서 걸러지지 않은 예외 |

필터도 크기별로 검증합니다(키 형식, 알 수 없는 필터 키, 중복, 누락, 크기 불일치). 문제가 있는 크기의 필터는 ✗로 표시하고 제외하며, 그 크기의 패턴은 `[스키마]` FAIL이 됩니다.

### 성능 측정 방법
- `time.perf_counter()`로 **MAC 함수 호출 구간만** 측정합니다(입출력, 파일 읽기 제외).
- 크기마다 예열 1회(측정 제외) 후 **10회** 측정해 평균(ms)을 냅니다.
- 입력은 생성기로 만든 N×N 십자가 패턴이고, 필터는 data.json의 Cross 필터(3×3은 data.json에 없어 생성기 필터)를 씁니다. MAC은 값과 상관없이 항상 N²번 연산하므로 입력 값은 시간에 영향을 주지 않습니다.

## 결과 리포트

### 1. data.json 분석 결과

```
총 테스트: 6개
통과: 3개
실패: 3개

실패 원인 분류: [동점] 3건

실패 케이스:
- size_5_1: [동점] |Cross-X| = 1.11e-16 < 1e-9 → UNDECIDED 규칙에 따라 FAIL
- size_13_2: [동점] |Cross-X| = 2.66e-15 < 1e-9 → UNDECIDED 규칙에 따라 FAIL
- size_25_1: [동점] |Cross-X| = 1.78e-15 < 1e-9 → UNDECIDED 규칙에 따라 FAIL
```

| 케이스 | Cross 점수 | X 점수 | \|차이\| | 판정 | expected | 결과 |
|---|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | 1.1e-16 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | 8.8 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | 14.4 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | 2.7e-15 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | 1.8e-15 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | 52.8 | Cross | Cross | PASS |

### 2. 실패 원인 분석

**진단: 데이터/스키마 문제도, 로직 문제도 아닌 "수치 비교" 범주의 실패입니다.**

1. **데이터/스키마는 정상입니다.** 6개 케이스 모두 키에서 추출한 N과 input 크기, 필터 크기가 일치하고, expected(`x`, `+`)와 필터 키(`cross`, `x`)는 정규화로 모두 해석됩니다. `[스키마]`, `[크기]`, `[라벨]` 실패는 0건입니다.
2. **로직도 정상입니다.** 점수 차이가 분명한 3건(size_5_2, size_13_1, size_25_2)은 모두 expected와 같게 판정됩니다. `[판정]` 실패도 0건입니다.
3. **실패 3건은 필터 가중치가 두 점수를 수학적으로 똑같이 만들도록 설계된 케이스입니다.** 실제로 어떤 칸이 점수에 기여하는지 확인한 결과는 다음과 같습니다.

   | 케이스 | 패턴 | Cross 필터 기여 | X 필터 기여 | 수학적 점수 |
   |---|---|---|---|---|
   | size_5_1 | X 모양(1이 9칸) | 중앙 1칸 × 0.9 | 대각선 9칸 × 0.1 | 0.9 = 0.9 |
   | size_13_2 | 십자가(1이 25칸) | 십자 25칸 × 0.3 | 중앙 1칸 × 7.5 | 7.5 = 7.5 |
   | size_25_1 | X 모양(1이 49칸) | 중앙 1칸 × 4.9 | 대각선 49칸 × 0.1 | 4.9 = 4.9 |

   한쪽은 큰 가중치 한 번, 다른 쪽은 작은 가중치(0.1, 0.3)를 여러 번 더하는 구조입니다. 0.1과 0.3은 2진 부동소수점으로 정확히 표현되지 않으므로, 여러 번 누적하면 오차가 쌓여 `0.8999999999999999`, `7.499999999999997`처럼 1e-16 ~ 1e-15만큼 어긋납니다.
4. **epsilon이 없었다면 세 건 모두 틀린 판정이 나왔습니다.** `>`로만 비교하면 size_5_1은 0.9 > 0.8999… 이므로 Cross(expected X), size_13_2는 X(expected Cross), size_25_1은 Cross(expected X)로, 세 건 모두 **expected와 반대**입니다. 판정이 나온 것처럼 보이지만 실제로는 반올림 오차가 결과를 정한 것입니다.
5. **누적 방식에 따라 오차가 달라진다는 점도 epsilon이 필요한 이유입니다.** 같은 값을 반복문 `+=`로 더하면 `0.8999999999999999`이지만, Python 3.12 이상의 내장 `sum()`은 오차 보정 덧셈을 써서 `0.9`가 됩니다. 즉 같은 데이터라도 구현 방식이나 Python 버전에 따라 `>` 비교 결과가 뒤집힐 수 있습니다. epsilon 정책을 쓰면 어느 방식이든 **UNDECIDED로 같은 결과**가 나옵니다.
6. **이 실패를 코드로 "고쳐서" PASS로 만들지 않았습니다.** epsilon을 줄이거나 동점일 때 한쪽을 고르는 규칙을 넣으면 숫자상 PASS는 늘지만, 판단 근거가 없는 결과를 정답처럼 보고하게 됩니다. 두 필터가 같은 점수를 준다는 것은 **이 필터 쌍으로는 두 패턴을 구별할 수 없다**는 뜻이므로, 올바른 개선 방향은 데이터 쪽(필터 가중치를 다시 설계하거나 expected를 판정 불가로 두는 것)입니다.

### 4. 시간 복잡도 분석

**측정 결과** (MAC 1회, 예열 후 10회 평균, Python 3.14.7 / Windows 11)

| 크기 | 평균 시간(ms) | 연산 횟수(N²) | 연산 1회당(ns) |
|---|---|---|---|
| 3×3 | 0.000640 | 9 | 71.1 |
| 5×5 | 0.001110 | 25 | 44.4 |
| 13×13 | 0.005590 | 169 | 33.1 |
| 25×25 | 0.019250 | 625 | 30.8 |

같은 측정을 세 번 반복했을 때 25×25의 연산 1회당 시간은 30.8 ~ 32.7ns 범위였습니다. 절대값은 실행 환경마다 달라지지만 경향은 같았습니다.

**O(N²) 근거**

1. **코드 구조:** `mac()`은 바깥 반복 N번 × 안쪽 반복 N번 = **N²번** 곱셈과 덧셈을 합니다. 입력 값과 무관하게 크기만으로 연산 횟수가 정해지므로 시간 복잡도는 O(N²)입니다.
2. **측정값:** 연산 1회당 시간이 13×13부터 약 31~33ns로 거의 일정합니다. 즉 **총 시간 ≈ 약 32ns × N²** 이며, 시간이 N²에 비례한다는 실측 근거입니다.
3. **배율 비교:** 13×13 → 25×25에서 연산 횟수는 625 / 169 = **3.70배**, 시간은 0.019250 / 0.005590 = **3.44배**로 거의 같은 비율로 늘었습니다. N이 약 2배가 되면 시간은 약 4배가 되는 O(N²)의 특징과 맞습니다.
4. **작은 크기의 편차:** 3×3, 5×5는 연산 1회당 시간이 더 높게 나옵니다. 함수 호출, 크기 검사, `perf_counter` 호출 같은 **고정 비용**이 N²과 상관없이 매번 들기 때문입니다. 연산 횟수가 9처럼 작으면 이 고정 비용이 총 시간에서 차지하는 비율이 커지고, N이 커질수록 N² 항이 지배해 연산당 시간이 일정한 값으로 수렴합니다. 그래서 시간 ≈ a·N² + b 꼴이며, 빅오 표기에서는 최고차항만 남아 O(N²)입니다.
5. **NPU와의 연결:** 25×25 필터 하나도 625번의 MAC이 필요하고, 실제 AI 모델은 수백×수백 크기의 필터를 수천 개 쓰므로 연산량이 크기의 제곱으로 폭증합니다. CPU의 반복문은 이 연산을 하나씩 순서대로 처리하지만, 각 MAC은 서로 독립적이므로 동시에 계산할 수 있습니다. NPU는 수천 개의 MAC 유닛으로 이를 병렬 처리해 같은 N² 작업을 훨씬 짧은 시간에 끝냅니다.

## Git 작업 흐름

단계마다 `feature/*`(문서는 `docs/*`) 브랜치에서 작업하고 `--no-ff`로 `main`에 병합했습니다. 커밋 메시지는 Conventional Commits(`feat`, `fix`, `test`, `docs`, `chore`) 형식입니다.

| 단계 | 브랜치 | 내용 |
|---|---|---|
| 0 | `main` | 프로젝트 초기화, data.json 추가 |
| 1 | `feature/core-mac` | Matrix 구조, MAC 연산 |
| 2 | `feature/judge` | 라벨 정규화, epsilon 판정 |
| 3 | `feature/mode1` | 모드 1 입력·검증·결과 |
| 4 | `feature/mode2` | data.json 로드·검증·케이스 판정 |
| 5 | `feature/perf-report` | 크기별 성능 분석, 결과 요약, 패턴 생성기 |
| 6 | `docs/readme` | README 작성 |
